## 0. 一句话

储蓄是**独立于收支的第二本账**：`saving_account`（账户）+ `saving_record`（流水）为底座，
余额 = `Σ(存入+转入) − Σ(取出+转出)` **纯派生、不落库**；存入/取出/转账/更新余额**不产生任何收入或支出**，
唯一与收支账本交汇的地方是记账页的两个开关（从储蓄支付 / 到账即存）。

## 1. 数据模型

### 1.1 `saving_account`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT | 主键 |
| family_id | BIGINT NULL | 账户归属家庭；**NULL = 全局预置账户**（5 条，所有家庭共用，见 1.3） |
| name | VARCHAR(32) | 账户名（重名校验在应用层，不加唯一索引） |
| icon / color | VARCHAR(32) / VARCHAR(16) | emoji / `#RRGGBB` |
| sort | INT | 越小越靠前（预置固定 1–5） |
| is_system | TINYINT(1) | 1=预置（**全局只读：不可改名/停用/删除**） |
| status | TINYINT(1) | 1=启用，0=停用（**仅自定义账户可停用**；不进新增选择列表，余额仍计入总额） |
| deleted | TINYINT(1) | 逻辑删除（MyBatis-Plus 全局 `logic-delete-field`，仅自定义账户） |

### 1.2 `saving_record`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| family_id / account_id | BIGINT | 家庭 + 账户（account_id 必填，未选择时默认「活期」） |
| direction | VARCHAR(16) | `in` / `out` / `transfer_in` / `transfer_out` |
| source | VARCHAR(16) | `normal` / `adjust`（更新余额生成的校准流水） |
| amount | INT | 恒为正整数（分） |
| date | DATE | **业务日期**，「本月存入/取出」按它统计（不加 time 列） |
| note | VARCHAR(200) | |
| openid / operator_name | VARCHAR | 操作人 + **昵称快照**（成员退出会物理删 `family_member` 行） |
| link_id | VARCHAR(40) NULL | 同表组合键（账户转账两条共享） |
| linked_transaction_id | BIGINT NULL | 跨表组合键（从储蓄支付 / 到账即存） |

索引：`idx_family_date`、`idx_family_account`、`idx_link`、`idx_linked_tx`。
**没有 `balance` 字段，也没有 `status` 作废态**（物理删除，与 `transaction` 的软作废刻意不同）。

### 1.3 预置账户 = 全局只读行

**规则（2026-10-22 用户确认）**：预置账户**不能停用**，只有自定义账户可以；预置账户同时不可改名、不可删除。

由此 `family_id = NULL` 的 5 行（活期/定期/国债/基金/保险）就是**所有家庭共用的真实账户**，
与 `category` 的全局预置分类完全同套路，不需要任何「按家庭复制」的逻辑：

* 可见集合 = `family_id = 该家庭`（自定义）**OR** `family_id IS NULL`（全局预置），预置固定排最前；
* 写入校验：`lockAccount()` 接受「本家庭账户」或「全局预置账户」，其余一律 `储蓄账户不存在`；
* 改动校验：`is_system = 1` 的账户对 `PUT /saving/account/{id}` 与 `DELETE` 直接 `403`，
  且**先判 is_system 再取家庭**（预置行 `family_id` 为 NULL，不能拿它去做家庭权限校验）；
* 余额/流水仍按 `(family_id, account_id)` 聚合，所以「A 家庭在活期上的余额」与「B 家庭在同一个全局活期账户上的余额」互不干扰；
* 停用状态只对自定义账户有意义，家庭级状态与全局行不再冲突。

### 1.4 五条硬规则（服务端落地位置）

| 规则 | 落地 |
| --- | --- |
| 余额永远派生 | `SavingRecordMapper.statsByAccount / balanceOf`；`SavingAccountService.balanceOf()` |
| 转账零和 | `SavingService.transfer()` 写两条共享 `linkId`，`periodStats` 不统计 transfer_* |
| 组合记录原子化 | 同表用 `linkId`（转账）、跨表用 `linkedTransactionId`（账单配对），删除落在一个事务里 |
| 方向不可改 | 所有更新入口都不接受 `direction`；账单侧改 `type` 直接拒绝 |
| 金额可改但受余额约束 | `cap = 该账户当前余额 + 原金额`（取出/transfer_out/从储蓄支付通用） |

## 2. 并发与一致性

余额是派生值，**没有 `balance` 列可以做 `WHERE balance >= ?`**。因此采用
「**行锁 + 锁内 SUM**」等价实现余额原子扣减：

```
BEGIN
  SELECT ... FROM saving_account WHERE id=? AND deleted=0 FOR UPDATE   -- 锁账户行
  SELECT Σ(in+transfer_in) − Σ(out+transfer_out) FROM saving_record ... -- 在锁内算余额
  -- 校验 / 写入
COMMIT
```

* 所有写路径（存入、取出、更新余额、转账、从储蓄支付）都先锁涉及账户；
* 转账**按账户 id 升序**加锁，避免两笔反向转账互等；
* InnoDB 可重复读下，一致性读的 read view 在首次读时建立，而首次读就是这条锁定读，
  因此锁内 `SUM` 一定包含前一个持有者已提交的数据——不会出现「两笔并发同时通过」；
* 全局预置账户被所有家庭共用，**不同家庭的并发写入会在同一行锁上串行**——这是刻意的，
  因为余额校验必须基于「锁内 SUM」；单家庭场景下无额外开销。

## 4. 关键规则实现

### 4.1 数字口径

```
储蓄余额 = Σ(in) + Σ(transfer_in) − Σ(out) − Σ(transfer_out)     // 单账户 or 全家庭
本月净增 = Σ本月 in − Σ本月 out                                   // 按 date，transfer 不计
```

「更新余额」产生的 `adjust` 走 `in`/`out` 方向，因此**自然计入余额与本月净增**，但**不进收支账本**。

### 4.2 更新余额（余额校准）

* 只接收 `actualBalance`，服务端算 `δ = actualBalance − bookBalance`；
* `δ = 0` → `400 余额没有变化`（先判 0 再判 24h，避免"没变化"被 24h 确认盖住）；
* 同一账户 24h 内第二次校准：无 `confirmed=true` → `409`，提示上次时间与差额（前端用 `/adjust/preview` 渲染二次确认）；
* 金额不可编辑（`PUT /saving/record/{id}` 改金额 → `400`），只能删除后重新校准。

### 4.3 编辑/删除矩阵

| 记录类型 | 可改 | 禁止 | 删除 |
| --- | --- | --- | --- |
| 普通存入/取出 | 金额、日期、备注、账户 | 方向 | 单条物理删 |
| 余额调整 `adjust` | 日期、备注 | 金额、账户、方向 | 单条删（余额回退） |
| 账户转账 `linkId` | 金额、日期（两条同步）、备注 | 账户、方向 | 两条一起删 |
| 组合记录 `linkedTransactionId` | 金额、日期（**与账单同步**）、备注 | 方向、储蓄账户、只改一侧金额 | **连同账单一起删** |

* 取出类金额上限：`cap = 当前余额 + 原金额`；换账户时按目标账户余额校验（`amount ≤ 目标账户余额`）；
* 关联账目已作废/已不存在 → 流水 `readonly=true`，编辑与删除都 `400`。

### 4.4 账户

* 新建：owner、名称去重（同家庭未删除账户 + 全局预置名）、自定义 ≤20；
* 预置账户：不可改名/图标/配色/排序、不可停用、不可删除（`403`），`deletable=false`；
* 停用（仅自定义）：不校验余额；停用后 `lockActiveAccount` 拒绝新增存取/支付/转账，但余额仍计入总额；
* 删除（仅自定义）：余额 > 0 → `400 该账户余额为 ¥X，请先转出到其他账户`；余额 = 0 → 逻辑删除；
* 已删除账户的历史流水靠 `listAllIncludingDeleted` 带的账户字典显示名称（不进可选列表）。

### 4.5 跨表联动（从储蓄支付 / 到账即存）

```
POST /transaction { type: expense, amount: 8000, savingAccountId: 3 }
  ├─ insert transaction (status=1)                       ← 进收支账本/预算/统计
  └─ SavingService.createLinked(): 锁账户 → 校验余额 → insert saving_record(direction=out, linked_transaction_id=tx.id)
     （余额不足 → 整个事务回滚，账单也不落库）
```

* `PUT /transaction/{id}`：`syncLinked()` 同步金额与日期，校验上限，拒绝改方向 / 改储蓄账户；
  若账目本无配对流水但请求带了 `savingAccountId` → `400`（不能事后追加联动）；
* `DELETE /transaction/{id}`：`deleteLinkedForTransaction()` 成对删除；
* 反向：`DELETE /saving/record/{id}`（组合记录）也会删除关联账单。

### 4.6 成员退出（"记账行为可以作废，资金位置不能作废"）

`TransactionService.voidByMember()` 改为走 `TransactionMapper.voidByMemberExceptSavingLinked`：

```sql
UPDATE transaction t SET status = 0, voided_at = ?, void_reason = ?, voided_by = ?
WHERE t.family_id = ? AND t.openid = ? AND t.status = 1
  AND NOT EXISTS (SELECT 1 FROM saving_record s WHERE s.linked_transaction_id = t.id)
```

* 普通收支流水：照旧软作废（`status=0`）；
* 与储蓄配对的**两个方向**（从储蓄支付的支出、到账即存的收入）都整对保留——只排除一侧会造出
  「收入作废、存入还在」的错账；
* 储蓄流水本身完全不动（余额不回滚），操作人靠 `operator_name` 快照展示。

### 4.7 家庭解散

`FamilyService.dissolveFamily()` 新增：`saving_record` 物理删除 + `saving_account` 物理删除
（账户表有逻辑删除标记，故走 `physicallyDeleteByFamily` 自定义 SQL）。全局预置账户（`family_id IS NULL`）不受影响。
